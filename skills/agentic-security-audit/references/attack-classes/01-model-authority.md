# 01 — Model authority

Trace decoded proposals into principal construction, role/risk flags, policy results, tool names and capability objects. Compare semantic contracts with direct-tool or legacy providers and fallback routes. Does a model field such as `approved`, `trusted`, `risk`, `tenant_id` or `is_admin` overwrite server-owned state? Can a nominally typed compiled action be constructed through a path that skips admission?

Require the controlling field, exact assignment/admission point, downstream checks and privileged effect. A controlled proposal fixture proves what software accepts; it does not prove a particular injection reliably elicits that proposal. Keep model-causation assumptions explicit.

Model-controlled intent or tool arguments are expected inputs in many architectures. Reject the claim when deterministic handler/resource checks preserve authorized scope and intended action. Structured output validates shape; it does not confer authority.
